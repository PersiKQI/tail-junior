# ТЭЙЛ API

Node.js 24+; встроенные HTTP и SQLite. Запуск из корня `teyl-app`: `npm run api`. По умолчанию слушает только `127.0.0.1:3001`; SQLite создаётся в `data/teyl.sqlite` и сохраняется после перезапуска. Для разработки на телефоне в своей сети: `HOST=0.0.0.0 npm run api` и адрес компьютера в `EXPO_PUBLIC_API_URL` клиента. Не открывайте этот HTTP-порт в интернет. Публичный пилот требует HTTPS, ограничений доступа, резервного копирования и настроенной очистки данных.

Переменные: `PORT`, `HOST`, `DATABASE_PATH`, `CORS_ORIGINS` (точные origins через запятую), `NODE_ENV`. В development web-запросы разрешены с localhost/127.0.0.1 на любом порту. Для LAN web нужно указать origin явно. В production разрешены только origins из CORS_ORIGINS. Запросы нативного приложения не содержат Origin. CORS не заменяет аутентификацию.

## Контракт

Все тела — JSON; предел 16 KiB. Все маршруты, кроме health и создания сессии, требуют `Authorization: Bearer <token>`. Случайный 256-битный токен возвращается только при создании; в БД хранится его SHA-256. Сессии не восстанавливаются между устройствами. Токен позволяет управлять всеми данными своего профиля, поэтому на устройстве нужен SecureStore. В браузере защищайте origin от XSS. Автоматическое истечение/восстановление сессии отсутствует в этом MVP.

| Метод и адрес | Тело | Результат |
|---|---|---|
| GET /api/health | — | 200 `{status:"ok",service:"teyl-api"}` |
| POST /api/session | `{}` | 201 `{token,state}` |
| GET /api/bootstrap | — | 200 AppState |
| PATCH /api/profile | часть `{name,ageBand,onboardingCompleted,reducedMotion,focus}` | 200 AppState |
| PUT /api/goal | GoalInput из shared/types.ts | 200 AppState |
| POST /api/lessons/:id/answer | `{choiceId}` | 200 AnswerResult |
| POST /api/simulations/:id/answer | `{choiceId,reasonId}` | 200 AnswerResult |
| POST /api/checkins | `{type:"saved",amount,note?}` или `{type:"reviewed",note?}` | 200 AppState |
| POST /api/assessment/answer | `{choiceId,reasonId}` | 200 AnswerResult |
| DELETE /api/account | — | 204; профиль, токен, ответы, события и отметки удалены |

Ошибки: `{error: "Текст для пользователя", code:"..."}`. 400 — поля; 401 — сессия; 403 — Origin; 404 — адрес/контент; 409 — закрытый шаг или окно; 413 — размер; 415 — формат; 429 — создание более 30 сессий с одного адреса за 10 минут; 500 — сервер. При 401 клиент предлагает новый старт, а не маскирует исчезновение данных.

`Idempotency-Key` на POST /api/checkins (1–80 символов A–Z, a–z, цифры, `_`, `-`) предотвращает повторное начисление при повторе запроса. Один ключ должен соответствовать одному действию. Повтор с тем же типом, суммой и нормализованной заметкой возвращает текущее состояние. Повтор с изменёнными данными возвращает 409 IDEMPOTENCY_CONFLICT. Проверка ключа, чтение актуальной суммы, ограничение накоплений и запись выполняются в одной транзакции. Без ключа каждое нажатие считается отдельной отметкой.

## Порядок и оценивание

Порядок: budget → goal → contribution → симуляция plan → income → expense → safety → симуляция change. Ответ на задание завершает шаг независимо от правильности. Ошибка получает подготовленное объяснение. Правильность каждой симуляции требует одновременно правильного действия и объяснения.

Первая попытка хранится неизменно. Повтор учебного задания доступен и возвращает обратную связь по новому ответу, но не меняет первую попытку и не создаёт повторное событие завершения. Это позволяет учиться без искажения метрики первой попытки. В bootstrap не передаются ключи правильных ответов или объяснения; они выдаются после отправки. Контент в server/content.ts — учебная версия `p0-2026-10-31-v2`, требующая предметной проверки перед внешним пилотом.

D7-проверка открывается ровно через 144 часа от первого содержательного ответа, закрывается в 216 часов. Часы сервера, а не клиента. В ней одна попытка с двумя элементами: выбор действия и причины. Пропуск не равен отсутствию навыка; состояния waiting/expired/completed различаются. Повтор отправки после завершения возвращает первый результат.

## Расчёт

Целые рубли 0–1 000 000, цель от 1 ₽, срок 1–120 месяцев, название 1–60 символов. Накопленное может превышать цель. `available = max(0, income − essential − reserve)`. `requiredMonthly = ceil(max(0,target − saved) / months)`. `projected = saved + monthly × months`. `feasible` требует неотрицательного бюджета, посильного взноса и покрытия цели. `suggestedMonths = ceil(max(0,target − saved) / monthly)` при положительном введённом взносе, иначе null; это математический срок при данном взносе, а не доказательство его посильности. Если взнос выше available, нужно сначала изменить взнос. Проценты, инфляция и доходность не моделируются.

Отметка saved — самоотчёт пользователя, а не подтверждённая банковская операция. Она увеличивает saved; reviewed не меняет деньги. Список возвращает последние 100 отметок. Пользователь может исправить накопленную сумму через редактирование цели; история отметок остаётся историей сообщений, а не бухгалтерским балансом.

## Данные и проверка

Профиль, цель и ответы связаны с псевдонимной сессией. Таблица событий хранит только session_id, имя события, content_id, timestamp, content_version; без имени, заметок и финансовых сумм. События: session_created, goal_created/revised, lesson_answered, simulation_answered, assessment_answered, saving_self_reported, plan_reviewed. Нет сторонних трекеров, обмена с банком и экспериментальной рандомизации. Повторный просмотр не считается действием.

Проверка: `node --test tests/backend.test.ts`. Покрыты расчёт и крайние значения, последовательность, повторы, неизменность первой оценки, отсутствие ключей ответов в клиентском состоянии, разделение сессий, перезапуск SQLite, удаление, окно D7, валидация, HTTP-аутентификация/CORS/размер запроса. Тесты используют временную БД и временный localhost-порт, не пользовательские данные.

## Бюджет и ближайшие действия (v2)

`AppState.budget` содержит `income`, `reserve`, `monthly`, четыре категории `categories[{id,title,amount}]`, `available` и `unallocated`. `PUT /api/budget` принимает доход, запас, ежемесячный взнос и все четыре уникальные категории: `food`, `transport`, `housing`, `other`. Заголовки назначает сервер; клиентский `title` не используется. Суммы — целые неотрицательные рубли до 1 000 000; сумма категорий также ограничена 1 000 000. Категории хранятся в SQLite, обновление бюджета атомарно пересчитывает связанную цель. При дефиците бюджет разрешено сохранить, чтобы показать проблему: `available=max(0,income−расходы−reserve)`, `unallocated=income−расходы−reserve−monthly`, последнее число может быть отрицательным.

У нового профиля без цели бюджет нулевой. Для старой цели расходы первоначально находятся в «Другое». Если редактирование цели через `PUT /api/goal` меняет общий `essential` без передачи категорий, категории сбрасываются: «Другое» получает новый итог, остальные — ноль. Это явное отсутствие детальной разбивки, а не выдуманное распределение. Если общий итог прежний, разбивка сохраняется. Доход, запас и взнос всегда синхронизируются между бюджетом и целью. `GoalSaveInput` допускает optional `categories` с той же схемой четырёх уникальных категорий. Их сумма обязана совпадать с `essential`; тогда цель и переданная разбивка сохраняются атомарно. Это используется для применения сценария, где дополнительная трата добавляется в «Другое» и остальные категории остаются прежними. При неверных категориях или несовпадении итога ни цель, ни бюджет не меняются.

Новые маршруты возвращают `AppState`:

| Метод | Данные | Поведение |
|---|---|---|
| POST /api/actions | `{type:"save",amount,note,dueDate}` или `{type:"review",note,dueDate}` | Планирует действие |
| PATCH /api/actions/:id | `{completed:true}` | Один раз создаёт самоотчёт и завершает действие |
| DELETE /api/actions/:id | — | Удаляет только невыполненное действие |

Дата — строгая существующая `YYYY-MM-DD`, от текущей календарной даты UTC до 30 дней вперёд включительно. Выполнить можно раньше или позже плана: это отметка пользователя, а не автоматический перевод. Одновременно допускаются 20 невыполненных действий. Список возвращает до 200: сначала все невыполненные, затем историю. Запланированное `save` требует суммы от 1 до 1 000 000 ₽; заметка до 200 символов. Для `review` описание — 8–200 символов и хотя бы два слова. Это технический минимум описания, а не автоматическая проверка качества размышления.

Завершение `save` увеличивает `goal.saved` и создаёт checkin `saved`; завершение `review` создаёт checkin `reviewed`, не меняя деньги. Вся операция — одна транзакция, включая проверку суммарного лимита. Повторный PATCH не начисляет деньги, не создаёт вторую отметку и не меняет время завершения. При завершении чужой ID даёт 404 без раскрытия принадлежности. При DELETE отсутствующий ID, в том числе чужой, возвращает текущее состояние своей сессии без изменений; повтор после потерянного ответа безопасен. DELETE выполненного собственного действия остаётся конфликтом 409. Завершённые действия нельзя удалить или переоткрыть; ошибочно указанное накопленное исправляется через редактирование цели. Новые события: `budget_updated`, `action_planned`, `action_completed`, `action_cancelled`. Планирование и отметка выполнения не являются подтверждением банковской операции или доказательством учебного эффекта.

## Интерактивные симуляции (v2)

`POST /api/simulations/:id/decision` принимает `{monthly,months,reasonId}`: месячный взнос 0–5 000 ₽, срок 1–12 месяцев, причина из `Simulation.reasons`. Обязательность предыдущих шагов и правило неизменной первой попытки сохраняются. Условия симуляций фиксированы и не читают личную цель, чтобы результаты отражали одинаковую задачу.

В `AnswerResult` добавлен `outcome`:

- `monthly`, `months`: выбранные значения;
- `available`: посильный остаток в условиях задачи;
- `projected`: прогноз суммы по выбранным условиям, либо null, если будущие поступления неизвестны;
- `gap`: нехватка до цели в прогнозе, либо null;
- `feasible`: финансово допустимо ли решение; правильность `correct` дополнительно требует верного обоснования;
- `remaining`: сколько не хватало до цели на начало данной ситуации (10 000 ₽ / 7 500 ₽).

Для `plan` допустим любой взнос не выше 2 500 ₽ и срок, при которых `2 000 + monthly×months ≥ 12 000`, с причиной `subtract`. Это позволяет, например, выбрать 2 000 ₽ на 5 месяцев. Для `change` допустим взнос 0 ₽ и причина `essentials`: текущих поступлений недостаточно даже для полного запаса. `projected` и `gap` равны null; `months` только эхо входа, не оценка срока. Клиент не должен показывать прогноз или менять оценку по этому полю для `change`.

Старый маршрут `/answer` сохранён для совместимости с прежним клиентом. Он делит ту же запись первой попытки с `/decision`; переход между маршрутами не сбрасывает оценку. Для новых числовых решений `choice_id` в answers содержит JSON с `mode:"decision"`, `monthly`, `months`; reason_id хранится отдельно. Версия текущего контента — `p0-2026-10-31-v2`; старые записи первой попытки остаются со своей версией. Для анализа пилота версии нельзя незаметно объединять.


### Повтор создания действия

`POST /api/actions` поддерживает optional `Idempotency-Key` с теми же ограничениями формата, что и отметки. Клиент сохраняет один ключ для всех повторов одного намерения. Тот же ключ и нормализованные `type`, `amount`, `note`, `dueDate` возвращают текущее состояние без нового действия и события. Изменение payload с прежним ключом даёт 409 IDEMPOTENCY_CONFLICT. Проверка повтора выполняется в транзакции до лимита 20 и текущего окна даты: повтор уже созданного действия работает даже после смены календарного дня. Для существующей SQLite-базы добавляется nullable `actions.idempotency_key` и уникальный индекс `(session_id,idempotency_key)`; старые действия сохраняются. Ключи ограничены своей сессией. После явного удаления действия его ключ освобождается; новый пользовательский замысел должен получать новый ключ.

## Предпочтение следующего действия

В `Profile` и bootstrap добавлены `focus: 'curious' | 'goal' | 'gentle' | null` и `focusUpdatedAt: string | null`. Это выбранное человеком предпочтение следующего действия: исследовать, приблизиться к цели или двигаться спокойно. Поле не является психологической оценкой, не меняет учебную последовательность, доступность заданий, результат попыток или прогресс.

`PATCH /api/profile {"focus":"curious"}` (также `goal`, `gentle`) сохраняет выбор и устанавливает `focusUpdatedAt` по часам сервера в UTC ISO 8601. Явный повтор того же выбора обновляет время; PATCH без `focus` оставляет оба поля прежними. `{ "focus": null }` очищает выбор и его время. Клиент не может передать `focusUpdatedAt`: это неизвестное поле и ошибка 400. Неизвестные значения, массивы и другие типы для focus также дают 400 без изменения профиля.

У новой сессии оба значения равны null. При запуске сервера миграция добавляет недостающие поля в JSON старых профилей со значением null, сохраняя имя, дату создания, настройки, цель и учебный прогресс. Существующий выбор и время не перезаписываются. Выбор хранится в SQLite и возвращается после перезапуска.

## Журнал ручных расходов

`AppState.expenses` возвращает все записи профиля (в том числе отменённые), без скрытой серверной пагинации. Схема записи: `{id, amount, category, occurredOn, note, voidedAt, createdAt}`. `amount` — целые рубли от 1 до 1 000 000, `category` — food/transport/housing/other, `occurredOn` — существующая дата YYYY-MM-DD не раньше 1900-01-01, `note` — до 200 символов. Журнал ограничен 500 записями **всего**, включая отменённые; предел явно показан в интерфейсе. При достижении лимита сервер возвращает 409 EXPENSE_LIMIT, а уже созданные записи остаются доступны. В интерфейсе фильтруемый список раскрывается по 20 строк с количеством показанных записей.

- `POST /api/expenses` принимает `ExpenseInput` и optional `Idempotency-Key`. Клиентский `api.expense(value,key)` всегда передаёт ключ. Повтор того же нормализованного amount/category/occurredOn/note возвращает существующее состояние без нового расхода. Другие данные с прежним ключом дают 409 IDEMPOTENCY_CONFLICT. Проверка повторов идёт до лимита и текущей даты.
- `PATCH /api/expenses/:id {voided:true}` отменяет запись; `{voided:false}` восстанавливает. `api.voidExpense(id,voided)` вызывает этот маршрут. Повтор того же состояния ничего не меняет и не создаёт событие. Чужой ID даёт 404. История физически не удаляется; удаление всего профиля очищает журнал через FK cascade.
- `ExpenseInput.timezoneOffsetMinutes` — optional целое от −840 до 720, знак соответствует JavaScript getTimezoneOffset(). Клиент передаёт текущий offset; сервер получает локальную календарную дату как UTC timestamp минус offset и запрещает будущую локальную дату. Это предотвращает ошибочный отказ вечером UTC, когда у пользователя уже следующий день. Без offset используется UTC. Дата хранится как выбранный календарный день и при просмотре не пересчитывается между поясами. Offset не входит в идентичность расхода, поэтому повтор после смены пояса не создаёт дубль.

Запись расхода **не меняет** месячный бюджет, цель, накопления или checkins. Это самостоятельный журнал самоотчётов, не банковская выписка. Итоги месяца и недели суммируют только неотменённые записи, месяц определяется локальным календарём клиента, неделя — с понедельника по сегодня. Сравнение по категориям использует текущий месячный план и записанные траты текущего месяца; оно не предполагает, что пользователь записал все траты. Траты прошлых месяцев доступны через «Всё время».

Новая таблица expenses добавляется при старте без изменения прежних таблиц. События expense_recorded/expense_voided/expense_restored содержат ID записи и время, но не суммы/заметки. Тесты: `node --test tests/budget-*.test.ts`; проверены идемпотентность, локальная граница даты, предел 500, отмена/восстановление, отделение от плана и накоплений, изоляция, HTTP, миграция, перезапуск и вычисления периодов.

## Учебные инвестиции

Модуль живёт отдельно в `AppState.investments`: `lessons`, `progress`, `lab`, `contentVersion`. Его шесть разборов не входят в основной маршрут из шести уроков и двух симуляций, не запускают и не сдвигают D7. Первый разбор и лаборатория доступны сразу, без цели и бюджета. Прохождение обозначает «разобрано», а не доказанное освоение навыка. Здесь нет банковских операций, рекомендаций купить инструмент или обещаний дохода.

`lessons[]` содержит `id, order, title, subtitle, duration, concept, example, question, choices, reasons, sources, completed, unlocked, firstAttempt, latestAttempt`. Последовательность: `horizon`, `deposit-bond`, `coupon`, `stock`, `fund`, `promises`. Следующий разбор открывается после валидного ответа и объяснения, независимо от правильности. Правильные ключи и итоговое объяснение отсутствуют в публичном содержимом до отправки ответа. Поле `correct` в сохранённой попытке относится только к уже отправленному ответу, а не является ключом задания. `progress` содержит `completedLessons,totalLessons,nextLessonId`.

- `POST /api/investments/lessons/:id/answer` — `{choiceId,reasonId}` → `InvestmentAnswerResult {correct,title,explanation,alreadyCompleted,state}`. Проверка обоих выборов на сервере. Первая попытка `{choiceId,reasonId,correct,createdAt}` неизменна; новый выбор обновляет последнюю. Повтор тех же двух выборов не меняет timestamp и не создаёт повторное завершение. История всех промежуточных попыток не сохраняется. Неизвестный урок → 404, закрытый → 409, несуществующие варианты или отсутствие объяснения → 400.
- `POST /api/investments/lab` — `{allocation:{cash,bond,stock,fund},scenarioId,reasonId}` → `InvestmentLabResult {correct,title,explanation,result,state}`. Разрешены ровно четыре категории, каждое значение — целое от 0 до 10, сумма — 10. Один пункт означает 1 000 виртуальных ₽. `scenarioId`: `growth|down|early`; `reasonId`: `risk|fund_safe|coupon_safe`. Любые неизвестные поля, сценарии, причины или неправильное распределение → 400. Клиент не передаёт итог: сервер вычисляет его сам.

`lab` содержит `allocation,lastScenarioId,lastResult,lastReasonId,lastCorrect,reviewedScenarioIds,updatedAt`. По умолчанию все 10 долей — `cash`, результаты и timestamp равны null, список просмотренных сценариев пуст. После разбора сохраняются последнее распределение/сценарий/вывод/результат и уникальный список сценариев, по которым отправлено объяснение. Неправильное объяснение тоже считается разбором, но `lastCorrect` остаётся false. Повтор одинакового запроса идемпотентен. В этой версии нет первого исследовательского ответа лаборатории и истории всех изменений портфеля; первая попытка хранится только для уроков.

### Вымышленная расчётная модель

Общий для UI и сервера файл `shared/investment.ts` экспортирует `evaluatePortfolio`, `validateInvestmentAllocation`, `INVESTMENT_ASSETS`, `INVESTMENT_SCENARIOS`, `INVESTMENT_LAB_QUESTION`, `INVESTMENT_LAB_REASONS`, `DEFAULT_INVESTMENT_ALLOCATION`, `INVESTMENT_MODEL_NOTICE`. Числа заданы для обучения; это не котировки, не статистика рынка и не прогноз.

| Сценарий | Период | Облигация: цена / купон | Акция: цена / дивиденд | Фонд: цена |
|---|---|---|---|---|
| growth | 3 месяца | +1% / +2% | +6% / 0% | +4% |
| down | 3 месяца | −6% / +2% | −20% / 0% | −12% |
| early | 1 месяц | −3% / 0% | −8% / 0% | −5% |

Проценты — за весь указанный период, не годовые; выплат по фонду отдельно нет. `cash` не имеет дохода, изменения цены и комиссий. Для инвестированной части начисляется комиссия 0,1% от начальной стоимости при входе и 0,1% от стоимости после изменения цены при выходе. Выплаты не входят в базу комиссии выхода. Каждое изменение цены, выплата и комиссия округляются до копеек до сложения, вычисления ведутся в целых копейках. Возврат в рублях: `initial,ending,cashIncome,priceChange,fees,profit,rows`; каждая строка содержит те же суммы плюс `asset,units`.

`ending = initial + cashIncome + priceChange − fees`; `profit = ending − initial`. Комиссия входа учитывается в конечном результате, а распределение задаёт условную начальную стоимость активов. Это сравнение сценариев, а не исполнимый приказ брокеру: модель не рассчитывает остаток денежных средств для оплаты покупки и комиссии, лоты, НКД или порядок списаний. Налоги, инфляция, дефолт эмитента, изменение ставок, ликвидность и дополнительные издержки не входят в числовой расчёт. Поэтому 10 000 ₽ в категории `cash` сохраняются номинально; это не утверждение о сохранении покупательной способности.

Пример проверки: 2 доли денег + 3 облигаций + 3 акций + 2 фонда в `down` дают изменение цены −1 020 ₽, купон 60 ₽, комиссии 14,98 ₽, итог 9 025,02 ₽ и результат −974,98 ₽. Положительный купон не исключает убыток. Отдельный пример третьего урока имеет другие заданные комиссии: 1 000 + 30 − 50 − 4 = 976 ₽, результат −24 ₽; он не выдаётся за сценарий лаборатории.

### Хранение и источники

Аддитивно создаются `investment_answers` и `investment_labs` с внешними ключами на сессию и `ON DELETE CASCADE`. Старые пользователи получают пустой модуль без изменения накопленного состояния. Данные изолированы по сессии, сохраняются при перезапуске и удаляются с аккаунтом. Первая отправка каждого урока и первый разбор каждого сценария записывают события `investment_lesson_answered` / `investment_scenario_reviewed` с ID материала и версией инвестиционного контента. В события не попадают суммы, распределение или личный текст. Данные модуля не изменяют цель, план бюджета, расходы, действия или отметки накоплений.
