# ТЭЙЛ API v2 — backend на Go

Реализация «ТЭЙЛ спецификация backend на Go v0.1» (1 ноября 2026). Замена Node/SQLite сервера
[tail-junior](https://github.com/PersiKQI/tail-junior) для аудитории 14–20 лет. Модульный монолит:
Go, `net/http`, PostgreSQL, pgx, goose. Один исполняемый файл в режимах `api` и `worker`.

## Состояние

Готовы **все пять этапов** §24 в объёме backend.

| Этап | Содержание | Статус |
|---|---|---|
| 1 | сессии, профиль, удаление, назначения, попытки, помощь, ответы, идемпотентность | готов |
| 2 | diagnostic/review наборы, сроки по якорям, скрытие оценки до финализации, partial/skipped, отзыв редакций, next-step | готов |
| 3 | лаборатория V2, XP и роли, бейджи, учебные свидетельства, учебные дни, защита серии, назначенный повтор | готов |
| 4 | денежный план, расходы, отметки, действия; импорт из SQLite и перенос старого D7; событие; косметика | готов |
| 5 | outbox и worker, экспорт аналитики, напоминания и dry-run доставка, телеметрия, 429 | готов |

Вне backend и не подтверждено здесь: обновлённый React Native клиент, разрешения push в мобильной
сборке (готовность Expo Go к remote push — не свойство backend), нагрузочная способность,
реальная доставка push и миграция реальной базы. Это подтверждают разработка клиента и пилот.

## Восстановленный комплект

Комплект JSON из спецификации не передан. Файлы восстановлены по тексту документа и
**требуют предметной проверки и утверждения редактором**:

- `content/learning-program-server-draft.json` — 24 learning, 3 diagnostic, 6 review, 12 терминов,
  маршруты starter (12) и full (24). L01, L07, L09, L13, L14, L19 адаптированы из уроков
  tail-junior, остальное составлено заново. `publicationStatus: draft`.
- `content/content-adapter.json` — допустимые пары для каждой карточки явно (L24 — две пары с
  общим объяснением), проверяемые исходы и связь с бейджами.
- `content/rules.json` — параметры правил из текста спецификации: XP, роли, бейджи, косметика,
  серия, уведомления, деньги, пределы частоты. Код читает их прямо из этого файла.
- `content/lab-case-LB01.json` — расчётный пакет `teyl-lab-budget-v2` (ставки и комиссия из
  спецификации) и кейс «Портфель с резервом». Формулировки составлены заново.
- `content/calculation-fixtures.json` — 9 итогов из приложения В и 2 подробные строки, сверенные
  вручную. Всё пространство 286 × 3 проверяется независимым расчётом на рациональных числах.
- `content/challenge-money-early.json` — событие «Деньги нужны раньше», витрина 9–16 ноября 2026
  (пример ритма), награда — аксессуар `acc-early-ribbon`.
- `content/notification-templates.json` — 15 реплик (5 поводов × 3 персонажа) без подстановок;
  три взяты из примеров спецификации.
- `content/legacy-d7.json` — карточка старого D7, перенесённая без изменений из `content.ts`.
- `contracts/openapi.json` — контракт всех маршрутов.
- `contracts/acceptance.json` — сценарии Given/When/Then со ссылками на тесты.
- `contracts/analytics-events.json` — схема экспортируемых событий и запрещённые поля.

Не восстановлен `data-model.json`: модель данных описывают миграции в `migrations/`.

## Запуск

Нужны Go 1.26+ и Docker.

```sh
make test-db   # PostgreSQL на 127.0.0.1:55433
make seed      # миграции, импорт комплекта, кейса и события, публикация (approved-by local-dev)
make run       # API на 127.0.0.1:8790 и worker в одном процессе
```

Проверка: `curl http://127.0.0.1:8790/api/v2/health`.

`teylapi -mode api | worker | all`. Переменные окружения:

| Переменная | Назначение |
|---|---|
| `TEYL_DATABASE_URL` | PostgreSQL (обязательно) |
| `TEYL_ADDR` | адрес API, по умолчанию 127.0.0.1:8790 |
| `TEYL_PUSH_KEY` | base64 32 байта, AES-256-GCM для push token; **одинаковый у api и worker** |
| `TEYL_ANALYTICS_KEY` | ключ HMAC псевдонимов пользователей в экспорте |
| `TEYL_WORKER_INTERVAL` | интервал проходов worker, по умолчанию 30s |

Без ключей процесс генерирует случайные и предупреждает в журнале: для разработки этого
достаточно, но зашифрованные токены не переживут перезапуск.

Публикация в пилоте: `teylctl publish -version <v> -approved-by "<редактор>"`, кейс и событие —
`publish-lab`, `publish-challenge`. Импорт создаёт только draft; сессии создаются лишь при
опубликованной поставке.

Отзыв редакции с существенной ошибкой:
`teylctl withdraw -item L03 -revision 1 -grading-revision 1 -reason "<что не так>"`.
Сначала публикуется поставка с исправленной редакцией — тогда открытые назначения получат
замену; без неё они закрываются как withdrawn. Наборы с отозванной карточкой становятся
invalidated; замена такого набора — отдельная административная операция (не реализована).

После обновления схемы локальную базу проще пересоздать: `docker compose down -v`, затем
`make test-db && make seed`.

## Перенос из текущего приложения

```sh
teylctl import-legacy -sqlite /path/to/teyl.sqlite -backup-dir legacy-backups
```

Импортёр копирует снимок в `legacy-backups/teyl-legacy-<sha>.sqlite`, читает только копию и
пишет рядом `.manifest.json` с числом прочитанных, перенесённых и пропущенных строк; та же
сводка сохраняется в `import_manifests`. Сначала проверять на копии реальной базы. Что
переносится:

- сессия → пользователь с тем же id и прежним `token_hash` (hex → bytes): приложение входит
  без нового старта; ageBand 21–22 → other, исходный профиль и focus — в `legacy_records`;
- бюджет и цель → план revision 1 (рубли × 100), расходы с `voidedAt`, отметки и pending-действия
  со связью с целью; у пересмотров `reviewedFields = unknown`;
- прежние ответы, инвестиционные попытки, снимок лаборатории V1 и выполненные действия →
  `legacy_records` с описанием ограничений; они не становятся L01–L24, свидетельствами, XP или
  кейсом V2;
- **старый D7**: окна, открытые или ожидавшиеся на момент переключения, продолжают работать
  через `GET /legacy/assessment` и `POST /legacy/assessment/answer` по прежнему контракту —
  окно 144–216 часов от первого ответа, один неизменный ответ, вне окна 409. Новые D7 не
  создаются; это не RS07, без XP и учебного дня. Статус окна есть в `bootstrap.legacy.d7`;
- события аналитики только считаются в манифесте;
- уже перенесённый пользователь при повторном запуске пропускается.

Порядок переключения писателя — §23: схема и импорт → сверка → проверка нового клиента →
короткое переключение. После переключения откат к SQLite требует обратной миграции.

## Устройство

- `cmd/teylapi` — HTTP API и worker; `-migrate` применяет миграции.
- `cmd/teylctl` — `migrate`, `validate`, `import`, `publish`, `publish-lab`,
  `publish-challenge`, `import-legacy`, `withdraw`.
- `internal/app` — сборка сервисов, общая для API, worker и teylctl.
- `internal/api` — маршруты `/api/v2`, аутентификация, пределы частоты, общий путь мутации.
- `internal/identity` — токен, профиль, удаление.
- `internal/learning` — зачисление, назначения, попытки, оценка, помощь, прогресс, следующий
  шаг, назначенный повтор, отзыв редакции.
- `internal/assessment` — наборы diagnostic/review: сроки по якорям, допуск, финализация,
  проекции без скрытых оценок.
- `internal/lab` — расчётная модель V2 (целые копейки), кейс, эксперименты, решения, расчёты,
  выводы и сравнение.
- `internal/progression` — доменные факты и их потребители: XP и роли, бейджи, свидетельства,
  учебные дни и защита серии, косметика, `GET /progress`; запись outbox вместе с фактом.
- `internal/money` — денежный план, расходы, отметки, запланированные действия.
- `internal/challenge` — событие поверх лабораторного кейса.
- `internal/legacy` — перенос снимка SQLite и контракт старого D7.
- `internal/notify` — настройки напоминаний, установка, шаблоны, выбор повода, квота, доставка.
- `internal/analytics` — экспорт outbox получателю аналитики.
- `internal/worker` — проходы outbox и доставки.
- `internal/ratelimit` — фиксированное окно для 429.
- `internal/content`, `internal/httpx`, `internal/idem`, `internal/store` — комплект содержания,
  строгий JSON и ошибки, квитанции идемпотентности, пул и транзакции.
- `migrations/` — схема.

Каждая мутация: проверка ключа и тела → транзакция: блокировка строки пользователя → поиск
квитанции → действие → запись квитанции → commit. Ошибка откатывает всё, ключ не расходуется.

## Решения, принятые при реализации

Обучение и проверки:

- Повторный ответ тем же выбором с новым ключом — 200 и прежняя квитанция; первая отправка — 201.
- Поддержка доступна только в незавершённой попытке learning/practice.
- Ручная практика — после первого принятого ответа по семейству; одна открытая на семейство.
- `public_response` квитанции хранится в jsonb: повтор возвращает тот же JSON с
  нормализованным порядком ключей.
- Отложенные пары создаются при зачислении; диагностика — только по запросу пользователя.
- Статус available у review вычисляется по dueAt при чтении: планировщик открытия не нужен.
- До открытия набора карточки показываются без названия и itemId.
- Закончить набор до срока нельзя (409 SET_NOT_AVAILABLE).
- Разбор карточки набора считается показанным в момент финализации.
- `assistanceUsed` берётся из журнала помощи; самостоятельность — ещё и из ранее показанного
  разбора семейства.

Прогресс:

- XP за review — по каждой отвеченной карточке, основание
  `review:{programLineage}:{slotFamilyId}:{familyId}` (максимум 700 XP предполагает 6 × 30).
- Если учебный пояс не выбран до первого зачётного ответа, фиксируется Europe/Moscow.
- Учебный день закрывают: первое принятие learning семейства, ответ в доступном review,
  назначенный повтор, решение, вывод и сравнение в лаборатории. Диагностика, ручная практика,
  деньги и старый D7 день не закрывают.
- Защита серии вычисляется хронологическим проходом при `GET /progress` и при зачёте дня.
- Назначенный повтор создаётся при `GET /next-step`, когда маршрут пройден и нет открытого кейса.
- Незавершённый эксперимент того же кейса возвращается повторно.
- Исправление оценок через correction record не реализовано.

Деньги, событие, косметика:

- `PUT /money/plan` требует все поля. Отметка saved и выполнение save увеличивают revision плана.
- Цель с тем же `goalId` правится на месте; без `goalId` создаётся новая (действия старой дают
  GOAL_CHANGED).
- Итоги расходов — через `?month=ГГГГ-ММ`; курсоры страниц непрозрачные.
- Событие: одно участие на семейство; эпизоды — из фактов связанного эксперимента. Своего XP нет.
- Открытая косметика остаётся навсегда; бейджи до появления каталога досинхронизируются.

Уведомления и аналитика:

- Доставка только dry-run (журнал и память процесса). Реальный провайдер подключается через
  интерфейс `notify.Provider`; включать его — отдельное решение после проверки мобильной сборки.
- Повод выбирается в момент слота по приоритету §18 (готовый review, незаконченная попытка, новый
  эпизод, мягкое возвращение через 3 дня без занятий, серия). Окно доставки — 120 минут после
  выбранного времени, вне тихих часов. После учебного действия сегодня приглашений нет.
- Квота: не больше одного за скользящие 24 часа и 3 или 7 за 168 часов; резервируется атомарно
  в транзакции до отправки, учитывает unknown и известные отказы.
- Отправка — вне транзакции. Известный отказ повторяется тем же notificationId (до 3 попыток),
  таймаут и зависшая после падения отправка — unknown без повтора.
- Автопауза на 7 дней после двух принятых приглашений без учебного возвращения за 7 дней;
  снимается учебным действием. Ручная пауза — `pauseUntil`.
- Push token хранится AES-256-GCM и наружу не возвращается; `PUT /device` без expectedRevision.
- Outbox пишется в одной транзакции с фактом и только при `analyticsEnabled`; экспорт — партиями
  с lease и SKIP LOCKED, повтор с нарастающей задержкой, после 10 попыток — dead. Получатель
  видит псевдоним (HMAC userId), а не userId. Получатель по умолчанию — журнал (dry-run).
- Без согласия на аналитику клиентские наблюдения принимаются и не хранятся;
  `notification_opened` отмечает открытие всегда.
- Пределы частоты — в памяти процесса: 20 сессий в час на адрес, 120 запросов в минуту на
  пользователя. `X-Forwarded-For` не учитывается: за прокси нужно будет настроить доверие.
